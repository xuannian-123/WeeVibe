# WG-04：主环节人工核实、成局与原安排补位恢复

本片依据原 Issue #4 和 [成局/补位规则](../11-首版成局加入与补位规则.md) §一.1–6、§三.1–8、实质变化后的保位说明。实现明确规则的一条完整小闭环，不等于整张 Issue 或安排变更/再次接受都已完成。

## 可操作闭环

1. 当前管理者即使本人不参加，也可对**当前主环节、当前安排版本**明确标记人工已核实。是管理者声明，不是系统查到库存；不写预订状态，不等于已成局。
2. 主段达到最低人数（不要求满员）、所有占位成员均接受当前版、人工核实满足后，管理者另行点击“确认／恢复主环节成局”。非主段人数不合并到主段。
3. 最低4/上限6时：4可确认；5退到4保留；4退到3原确认失效。原申请/批准流程补回4后不会自动恢复，管理者需要明确恢复；未改原安排不要求旧成员重填。
4. 只退出非主段不影响未受影响主段。退出/补位不自动改时间、最低人数、参考费用、外部预约，不退款或自动分摊。
5. 撤销主段人工核实会清除三项旧成局确认字段。重新标记已核实**不会复活旧确认**，仍需满足条件并人工确认。

## 本片时间范围

- 已有报名截止只约束新人申请/批准，不拿它冒充成局截止；截止已过但主段未开始，满足条件仍可操作。
- 开始后的首次核实/确认/恢复规则尚未明确。本片**新命令**在服务端和界面均未启用，准确提示“规则待确认，暂未启用”；这是交付功能范围，不是宣称用户规定禁止。
- 已成功原请求的幂等重放只读取当前快照，不重做核实、确认、版本或事件；因此它可核对开始前已经处理过的请求，但不开放开始后新操作。

## 接口与权限

`POST /api/v1/activities/:activityId/formation`，继续现有 Bearer 身份与 HTTP/cloud-http 适配；返回原 `ActivityDetail`，不新造活动状态。

共同严格字段：`idempotency_key`、`expected_revision`、`segment_id`、`expected_plan_revision`。

- `action: "set-verification"`，另带 `verified: boolean`。
- `action: "confirm-formation"`。

未知 actor/人数/已接受/预订字段不被接受。目标只允许当前主段，权限从已验证会话与数据库当前管理归属确定，不信客户端角色。

写入复用原父活动锁、Serializable 整事务与重试、actor+key+scope+fingerprint 幂等机制；**当前管理权先于重放复验**，旧管理者不能拿旧键重新获得权限。锁后采样时间并检查版本/主段/开始边界。核实状态、活动 revision、事件及去重键在同一事务中落地；确认同时记录现行 mainRevision/planRevision。未修改报名/批准/退出事务。

`FORMATION_NOT_READY` 表示人数、当前接受或核实未满足；`FORMATION_RULE_UNCONFIRMED` 表示本片开始后能力未启用，不伪装成缺少凭据或数据库故障。

## 客户端安全与反馈

确认前同步锁；取消/失败释放。真正发出 POST 前再次同步核对显示来源 session、`/me` actor、页面代次及活动/权限快照。隐藏/卸载使旧操作失效；已发请求不能保证撤销，晚结果不更新新页面或清掉原键。

同屏核实/成局、申请、审批、退出/晚到、邀请互斥；自身忙碌不会把自己判为过时。原请求仅同 actor 可人工核对重试，不自动发送；成功200只展示返回的当前状态，不能在旧键重放后把已失效状态说成再次成局。比当前读取旧的结果及不同 session 的结果不再展示。

## 实际验证层级

新增测试调用真实规则、服务编排、父锁装载、幂等和快照代码，以事务客户端替身串联确认→退出→申请审批补回→恢复；另有真实 route 函数、客户端、组件/详情页测试。覆盖最低/上限分离、全部占位接受、核实与预订分离、撤销不复活、旧管理员重放、陈旧版本、同键去重、锁等待跨开始、未知恢复、正向互斥。

这些不是 PostgreSQL 并发或微信原生实测。真实业务数据库脚本此前受执行器限制，未绕过重试；第9条原答卷迁移仍未实库应用。本片无新表/迁移、无真实模型/地图调用、无上线。最后自动测试和构建结果以交付日志为准。

## 回退与剩余

保留 v13 源码/dist 独立快照。源码回退不等于数据库回滚；既有字段里的人工核实/确认及新事件不会因换旧包自动撤销，也不应通过删数据伪装回退。不要恢复旧无条件答卷写入口。

本片不接安排变更/成员重接受、撤回申请、管理交接、改预约、支付或AI协调。前述“确认／恢复”不是需求问卷的“记录最终选择”；后者仍只记录建议，不会自动替换正式活动。相关明确的下一核心规则可独立实施，不因生产未部署而取消。
