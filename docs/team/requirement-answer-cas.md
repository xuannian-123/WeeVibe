# 单答卷版本冲突与旧请求重放保护

## 修复的问题

问卷的 `collection.revision` 只追踪题目/发布状态，不能代替每人的答卷版本。原实现允许 A 已保存、B 已更新后，网络重放旧 A 又覆盖 B。现在两种版本分别校验：

- `expected_revision`：仍是问卷版本，原含义不变。
- `own_response.response_version`：本人已保存答卷的独立递增整数。
- `respond.expected_response_version`：必须等于客户端已核对的本人答卷版本；首次保存必须为 `0`。
- 只有首次创建才生成版本 `1`，每次接受的更新严格加一。相同内容、相同毫秒时间也不能复用旧版本。

服务在既有活动/问卷父锁之后读取当前认证用户的答卷版本；已有答卷还用包含版本的条件 UPDATE，首次保存由复合主键保证每人一份。沿用 Serializable 事务及整笔重试，不在失败事务中继续写。参与者 ID 不从请求中接受。截止、手动关闭和取消规则仍在服务端校验。

## 冲突和兼容行为

旧版客户端缺少 `expected_response_version` 时，服务返回 `409 VERSION_CONFLICT` 并说明需要更新小程序/重新打开答卷，**不会静默当作无条件覆盖**。解析器允许缺字段仅为给出清晰升级错误，不代表可以写入。

原请求已经成功但响应丢失时，原版本重试也返回冲突；它**不是幂等成功回放**。前端保留当前输入，禁止冲突后直接反复提交；用户可先复制不含私人地点的草稿，再刷新并明确确认加载服务器答卷。取消确认保留输入。冲突错误不含其他人答卷、私人地点或原始数据库错误。

新客户端收到缺少答卷版本的旧后端快照不会猜测版本后提交，而会提示核对前后端版本。这不是登录失败，也不能通过改变 AppID 或会话绕过。

## 增量迁移与安全回退

`20261026141500_requirement_response_version` 只增加 `RequirementSubmission.responseVersion INTEGER NOT NULL DEFAULT 1` 和正数约束；旧答卷、公私字段、用户与问卷归属均不改写、不删除。已有答卷迁移后从版本 1 开始。

本轮仅完成迁移源文件与离线 Prisma 生成/校验；**没有执行该新迁移，也没有部署后端**。此前 8 条隔离数据库迁移通过的证据不包含这第 9 条。

未来获授权部署时，必须先备份、暂停/隔离旧版写入，再应用迁移并统一切换到匹配版本后端/客户端。不可在旧后端仍执行无版本写入的混合发布状态下声称 CAS 有效。

如需回退，保留新增列及全部答卷数据；回退旧服务之前关闭答卷写入口，或回退到仍保留 CAS 的兼容代码。**不能直接恢复旧无条件写入服务继续开放答卷**。源码回退依据保存在交付的本轮增量快照/校验中；不要通过删表、清答卷或重置计数解决冲突。

## 验证层级

- 新的离线服务 transaction-double 测试复现 A→B→重放 A，验证冲突与 B 保留、重复首次提交、旧客户端拒绝、身份隔离、条件 UPDATE 与截止等边界。
- React/jsdom 组件测试验证前端请求版本、冲突刷新、确认/取消、丢响应、重复点击和账号变化；Taro/网络为测试替身，不是微信真机。
- `scripts/check-requirements-integration.ts` 已对齐新协议并加入真实库重放检查源码，但此前执行器限制仍在，未重新尝试执行受阻路径；不能将离线测试称为真实数据库并发通过。
- 严格微信群权限仍保持关闭，不因本修复扩大发布权限。
