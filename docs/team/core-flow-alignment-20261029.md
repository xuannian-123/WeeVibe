# C 展示与朋友出游、团建流程集成

2026-10-29。本工作区采用另一对话已确认的 C 展示快照（108 个文件，快照提交 `5c94cbe`），保留本对话的地点来源、地图入口、可信身份、隐私与未知提交结果保护。未修改另一工作区，也未更新 main 或共享环境。

## 本轮产品规则

- 灵感沿用“干什么”的吃、喝、玩分类。约大家去直接进入本次活动昵称；带入地点所属按钮、具体地点文字、地图来源及坐标。示例为喝／咖啡，文字“咖啡：肯悦咖啡（林泉店）”。首次默认确定，允许本人取消；修改其他题不丢失地点，取消后再次读取不会强制恢复确定。
- 填表与小橘头共享同一出发地控制器，仅保留地图选择出发地入口、手动输入和既有清除坐标操作。私人预算、出发地不进入模型或其他成员视图。
- 小橘头五题都答过后，返回修改预算等历史回答，下一题继续向后走；不再因找不到未答题而停留原题。0—100 元为有效预算。
- 两种填写方式的“哪些内容已经确定了”仅显示日期及吃、喝、玩。想要、想避开、时间说明、补充、预算和出发地不在此页；原始偏好仍保存。保存端同样清理非允许范围的确定标记。
- 团建候选地点超过一个时，设计、试填、实际填写、提交校验、局头统计和模型汇总都使用同一派生首题。单选必答，保留其他输入；选项 ID 使用稳定地点 ID。零个或一个候选不插入首题，其他题号顺延。已有人提交后，不能静默改变这道题的地点集合或名称。
- 朋友先各自从多套推荐中选择偏好，再由局头协调一套，随后每位已填写成员显式确认。有人不同意进入调整，重新发起确认会清空上一轮确认；未回复、读消息、选择偏好都不等于接受最终安排。
- 团建由局头根据公开问卷统计生成并确认方案，成员只收到最终安排，不能查看他人答卷或统计。不要求全员确认团建方案。

## 实现边界

新 `/api/v1/gatherings/[id]/workflow` 使用真实身份、活动父行锁、各人选择版本、协调版本、方案轮次、来源指纹与持久幂等键。填写或成员变化使旧轮次失效；所有人确认后写入原最终安排字段，锁定后续填写。旧直接定案入口不能绕过新规则；已定案历史记录仍可读，同一已完成请求可回读。

追加 migration18 `20261029183000_gathering_workflow`，新增流程状态及命令表。原填写事件版本唯一性保留为部分唯一索引，新增生命周期事件复用站内消息和持久通知队列。团建最终安排检查约束与服务端规则同步扩展；不改历史迁移。共享运行角色届时需要新两表的必要 CRUD 权限。

客户端持久保存未知写入结果的原请求，显式重试沿用原幂等键；刷新或读消息不代表确认。轮次／版本过期及身份变化会拒绝旧请求，重新生成也不能用晚到结果覆盖已完成安排。

## Linux 并发复核补充

Linux CI 首次运行在同时确认的提交阶段出现停滞，未据此部署。新流程命令改用活动父行锁下的 READ COMMITTED 事务，等待者获得锁后读取最新轮次与确认状态，保留来源、版本和幂等检查；其他业务事务隔离级别未改变。隔离 PG 已通过新增三轮同时确认；脚本增加60秒总时限，避免并发回归停滞拖完整个CI。迁移18的SQL和数据库结构没有因该修正改变。
