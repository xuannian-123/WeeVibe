# 朋友出游 · 定案后完整安排与成员入口

2026-10-30。本轮承接方案选择至全员定案，逐项核对参考稿 P03、P05、P06，以及相关分享和异常读取。筹备定案与正式活动的报名、占位、付款仍按原设计区分；本轮没有新增正式活动转换流程。

## 修正的行为

- 修正定案后从内容整合进入活动安排仍列出全部候选的问题。结果页、活动安排、完整详情与环节详情统一根据服务端 final_choice 的 generation_id／plan_id 读取最终方案，不以列表第一项或旧选中状态代替。
- 修正定案详情仍显示“历史推荐／重新生成”提示的问题。P05 现在是独立的 C 风格完整安排页，带活动名称、日期、发起人、当前查看身份和只读提示，显示真实方案地址、说明、费用说明及待核实项。
- 记录各查看入口及滚动位置。完整安排→本人填写→返回，完整安排→环节→返回，以及从活动安排卡片返回，均回到实际来源，不统一跳到结果页或候选列表。
- 原成员只能查看本人的已保存填写；未提交的私密草稿不会在定案只读内容中冒充已保存记录。分享访客没有本人填写、成员填写、重新生成、报名或付款入口，仍可查看与转发最终安排。
- 历史定案记录没有 workflow 时，沿用其保存的最终选择；不要求重新生成，不声称历史记录已经过全员确认。完整方案缺失时保留读取提示，不拿其他候选替代。
- 分享标题标明“安排已定案”，路径仍只使用原活动 ID 与 entry=share，不携带答卷、确认内容或私密字段。

## 状态、权限和读取恢复

客户端继续使用现有 GET gathering、members、generate、workflow 及共享协议，没有变更后端接口、共享契约、数据库或生产业务规则。

- 增加最终状态一致性核对：锁定标记、最终 generation／plan、工作流阶段、确认人数须相符；访客响应不得夹带本人答卷、成员内容或协调记录。矛盾数据不进入结果页，也不用于分享。
- 浏览器检查发现原前台恢复回调捕获早期 identity，使同一账号的网络刷新失败也会清掉已读取记录。现在按该次读取绑定的 session 判断来源；短暂失败保留同一账号的记录并标明缓存来源。
- 读取失败后暂停新业务写入；重新读取成功或验证过的新写入回执恢复后才开放。已有填写草稿保留，暂停时可查看已保存内容，不伪称活动已经定案。
- 401／403／404、身份变化等访问失效情形隐藏旧记录；即便错误正文不符合契约，也依据这些 HTTP 状态隐藏旧私密内容。
- 原请求的幂等恢复继续保留，不自动重发。最终定案、完整详情及本人只读页不发起业务写入。
- 小橘头的问答顺序、回答解析和模型调用未更改；本轮仅增加读取尚未核对时的临时只读反馈。
