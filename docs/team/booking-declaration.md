# WG05：当前安排的人工预订声明与历史

依据[第11号规则](../11-首版成局加入与补位规则.md)第14、17、78–79行及WG05“核实预约声明”：每段独立记录预订状态，成局、地点可用性核实和预订互不替代，旧预约必须关联其原场馆/时段。本片只是**管理者人工记录**，不是商家接口下单、支付或核验订单。

## 单向首片

当前管理者即使本人不参加，也可明确选本活动尚未取消、未开始且当前预订状态为unknown的段，查看场馆/地址、起止/时区后确认“我已在系统外自行核对，现在记录人工预订声明”。报名已截止不阻止此声明；主段已开始不误挡另一个未开始段。新操作只支持 `unknown → manual_booked`。

**本片不提供撤回/订正标记**，因为未找到该反向操作的明确原文；更不执行退订、退款或自动取消真实订单。开始后新声明本片暂未启用，这是保守能力范围而非用户永久禁止。不能把这些首片边界说成完整预订管理已完成。

只更新本段bookingStatus、活动revision、不可变声明事件与原请求记录；**不改变**manual_checked、成局确认、主段/管理权、时间地点费用、人数要求、安排版本、旧接受、占位或申请。不因“已预订”自动核实、成局或代成员接受；没有订单/付款真实性保证。

## 声明绑定原安排，不造旧历史

服务端从锁后的当前安排生成白名单声明快照：原公开场馆名称/地址、原开始结束、时区、当时plan/activity版本、服务端时刻、unknown→manual_booked及固定人工来源。客户端不能指定旧场馆/订单字段；不收订单附件、账号、付款信息、私人地点、答卷或任意证据URL。

事件和状态同一事务保存，应用代码不更新或删除旧声明；这不是宣称数据库已强制禁止修改。仅存segmentId或事后读取当前场馆不能替代原安排快照。历史必须以当时记录显示，不能拿今天地址补造旧场馆。延期、上限、换主、交接、取消不改写原声明。

旧数据已有manual_booked却没有可信声明事件时，只能显示“旧人工标记，声明历史未提供”，不补造发生时间、操作者或原场馆。没有可验证记录不代表外部从未预订。以后若实现时间/地点writer，仍须另验新安排不可继承旧核实/预订、旧记录保留；本片不冒称全部换场历史已闭环。

## 当前管理者的本段历史

GET `/api/v1/activities/:activityId/segments/:segmentId/booking` 仅当前管理者可读，同一RepeatableRead快照先校当前权限与段归属，再查询专属声明事件。原管理者交接后无权；活动/段取消或开始后，当前管理者仍可只读历史并负责线下处理。公开详情仍只用原booking_status，不新增公共原始事件流。

投影只给记录时刻、当时公开场馆/时段/时区及版本、固定人工来源，不给actor UUID、原始事件detail、其它事件、私密资料或订单。声明是否与当前场馆/时段一致按保存字段比较，不能仅因planRevision相同便声称同场馆，也不能因最低人数变化便判定外部预约作废。

本片最多核对50条专属记录，取第51条只用于检测超限；超限或坏记录明确不可核验，不静默丢弃/截断后称完整。界面区分可信历史、未记录可核声明、旧标记缺历史和不可用。404/403/缺配置/畸形200不等于零记录，不因历史读取失败清预订标记。

历史仅在主动点击时读取；新声明成功后刷新当前详情并清除旧历史，提示手动重读，避免把旧页当最新。

## 并发、恢复和身份

新POST同一路由，严格原key、活动/计划版本及原unknown来源；当前管理者权限先于成功旧key恢复。复用父活动锁、Serializable整事务与CAS，锁后/写前采时，故障全回滚。成功旧key返回当前授权事实，不能把后来的状态或管理权恢复成旧值；未处理原key会重新核条件，所以未知重试不保证全是只读。

确认框前同步锁；取消/失败释放。本人source/session、活动/段版本、页面代次在身份检查后与实际transport前重验，观察过的A→B→A也不复活旧请求。读与写都隔离旧身份、离页/卸载、晚返回和旧finally；自身busy不导致自锁，同屏其它写入互斥。

首次请求等待身份时跨开始不再新发；已发请求不能保证撤回，合法成功迟回不能只因时钟变晚而丢原key。未知或不一致成功保原body/key；不生成新键绕过、不跨账号恢复私人草稿。明确已未发出的拒绝保输入，不假确认业务成功。
