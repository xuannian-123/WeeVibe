# 账户成功响应与私人页面来源保护

## 实际修复

HTTP 200 不保证是匹配的账户数据。此前 `{ "ok": true }` 会使 GO/收藏页面崩溃，资料保存会错误触发成功回调并关闭表单。本轮用实际组件和客户端、仅替换传输的探针复现，再修复。

- 新 `platform/account-api.ts` 校验账户 GET 与资料、收藏、已读更新成功响应；缺字段、错类型或不兼容结构统一作为 `INVALID_RESPONSE` / 写入结果未知处理，不回显原始数据或校验诊断。
- 无效成功不关闭资料、不调用保存回调、不删除收藏、不弹“已收藏”，也不在页面把消息显示为已读或跳转。请求可能已在服务器提交；未知响应不表示肯定未写入。输入仍在当前编辑器；用户可核对状态后重试。没有承诺跨关闭/重启保存本地稿。
- 接受真实服务的空字符串资料和 nullable 地点/邀请字段。旧响应没有 `activity_records` 时保持缺失，GO 仍明确只是旧 joined 列表；不伪造完整记录。其他已存在的核心数组（例如 favorites）必须有效，不能为了放过损坏响应一律补空。
- 未知额外字段被剥除。账户 JSON 中的任意 `avatar_url` 不作为可信头像；持久头像仍由独立校验、账号绑定的头像适配器加载。
- 读取失败展示“账户数据尚未读取/暂时无法确认”，不把 404 或不兼容数据说成“没有新消息/没有活动”。已有旧后端的明确空数组仍可以显示真实空列表。

## 会话来源而非只看挂载时间

审计还复现了更严重的场景：A 数据仍显示，令牌已换成 B，B 刷新未结束时打开资料，旧实现以挂载时 B 令牌绑定 A 的初始资料，能够向 B 提交 A 昵称。

- Home 的持久快照记录 `accountSession`，仅当其与当前会话一致才展示；切身份开始刷新时清旧快照并关闭旧私人子页。打开资料时再次检查来源。
- `ProfileForm` 必须接收初始快照的 `ownerSession`，不从当前挂载令牌猜来源。来源不同、退出或切账号时隐藏旧私人输入，不向新身份重放。
- 收藏和已读请求同样绑定展示它们的会话，并拒绝切账号前后返回的数据。
- **同账号临时刷新失败与切账号不同**：已打开资料表单的未保存本机输入在同账号 404 刷新后保留，不因重取失败重建表单；切身份则隐藏/隔离旧输入。账户尚未读到时不会新开空白资料表单覆盖未知服务器资料。

## 测试层级和限制

回归包括畸形 200、HTML404、旧可选字段兼容、空资料/nullable 字段、原始私有 sentinel、未知收藏/已读不假成功、同账号刷新保输入、A→B 刷新与未刷新两种资料来源场景。独立审计还用实际 `accountSnapshot` 加数据库替身产生投影，再送入真实客户端校验。

这不是实际 PostgreSQL、原生微信或生产联调；客户端校验不是授权依据，服务端本人身份过滤仍是主要边界。本轮没有修改服务端业务、契约、迁移、配置、地图/模型服务、邀请权限或部署。邀请客户端原已有成功 schema，本轮未改。
