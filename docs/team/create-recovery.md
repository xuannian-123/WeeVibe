# 创建被拒绝与未确认请求的恢复

2026-10-25。手机反馈：创建多环节活动时显示网络失败，原请求被锁定，不能查看或修改日期。失败草稿的具体时间未取得，不能直接认定由某个日期导致。

## 已复现的传输问题

实际开发工具中，原生云HTTP对无效创建请求进入fail回调，仅给出HTTP400和SDK通用错误，未提供业务响应正文；此前客户端统一当成网络中断，因而保留请求并锁定编辑。真实SDK另已成功创建一场未来时间的两环节诊断活动，两段均保存且各有发起人1席；它不是用户手机创建成功的证据。

修复采用显式传输头X-Weego-Response-Envelope: 1。后端通过HTTP200传送带版本标识的原始状态码与正文，客户端严格解包后继续使用同一业务错误、权限和重试规则。普通HTTPS请求没有此头时保留原状态码。该头不授予身份或管理权，身份验证仍先于创建、申请和审批。真正的SDK失败、不可验证响应及服务异常仍保留原请求。

协议定义在packages/contracts/src/cloud-http.ts，客户端适配在platform/cloud-http.ts，服务端统一在server/http.ts；使用handle的接口显式传入当前Request。后续接口沿用这一约定，不能为了规避SDK错误而把拒绝伪装成业务成功。

## 用户恢复路径

1. 请求结果未确认时，展示原请求的两段日期、时间、截止及参加选择；保留原编号，先核对并重试原请求。
2. 服务端若已创建，沿原编号返回已创建活动；不再次新建。
3. 服务端若明确拒绝并回滚，移除待确认锁，保留本机草稿供修改。用户应看到时间/版本/名额等实际业务提示。
4. 新请求在预览前及确认时检查本人所参加环节是否已开始或已截止，并指出环节名称。旧待确认请求仍须到服务端核对，不用本机时间检查跳过重放。

不清空账号缓存，不随意丢弃未知结果的请求，不自动换新编号重发。单次失败后也不能直接说明数据库没有记录，需分别核对。

## 部署与验收边界

修复需更新演示API及小程序；仅合并源码不代表云端已经生效。原账号改名待用户明确新名称，当前未提交。已添加第二微信的查看开发版/体验版权限，用户反馈同一手机切换两微信登录成功、B未出现A旧活动；同机双微信主流程已完成，本轮不要求双手机。

本次没有数据库迁移、付费、旧Secret重置、体验版替换或正式发布。实际部署、原请求恢复及手机结果继续单独记录。
