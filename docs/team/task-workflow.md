# 后续改进与新增任务怎样归类

2026-10-25。WG-01～WG-12是当前产品范围的起始拆分，后续可以调整原任务、拆子任务、增加新任务或暂缓，并非永久只能有12张卡。

## 判断标准

| 情况 | 通常怎样处理 | 例子 |
|---|---|---|
| 未完成任务内的完善、缺陷、验收补齐 | 继续原任务，更新本轮目标/清单和进展 | WG-02减少创建填写、优化布局、补地点填写；WG-03完善申请与审批状态 |
| 一张任务过大，需要分工或独立跟踪阶段 | 在原任务下关联子任务，原卡保留整体验收 | WG-07可分别跟踪真实模型适配、差异预览、确认应用；是否实施仍由范围决定 |
| 新的独立用户能力，可单独定义结果和验收 | 新建任务并关联依赖/受影响模块 | 若团队以后决定做“日历同步”，可独立成卡；此处仅示例，不表示已采纳 |
| 已完成任务之后的新改进或新缺陷 | 通常新建后续改进/缺陷任务，关联原卡和相关PR | 已交付创建后，再做另一种创建模式；若原验收误判或同一问题并未解决，可按事实重开原卡 |
| 跨多个模块的共同改进 | 设一个主任务/协调项，关联受影响任务，避免多张卡复制同一需求 | 全局组件/交互规范调整，或涉及创建和详情的数据契约变更 |

一次改动是否新增任务，主要看它是否有独立目标、验收、负责人协作或排期需求，不按代码行数判断，也不要求前端/后端各开一张卡。很小的同范围修正可以随原任务的PR一起完成。

## 保持完成条件清楚

每张任务写清本轮要解决的用户问题、范围、验收条件、代码模块及依赖。未纳入本轮的新点子先进入待讨论/后续清单；讨论后再决定放原卡、子任务或新卡，避免原任务不断扩张而无法收尾。

范围变更时同步受影响的业务规则、共享契约、数据模型、页面及任务依赖。任务描述可以调整，调整理由和当前完成标准应留痕。功能牵头人推进结果，可找协助；不按任务永久固定个人前端/后端岗位。

## 用在当前项目

- 用户认为发起界面不够省事，当前WG-02尚未完成：继续在WG-02讨论和改进即可。
- 高德选择器仍属于已有地点能力范围；AI入口/模型/确认应用仍在WG-07范围中收敛，较大部分可独立子任务跟踪。
- 完成后的独立增强或明显新增产品能力再增加后续任务，不必把所有想法都塞回原12张。
- 当前代码模块拆分属于工程/协作准备，进展记入WG-01及受影响任务；不因此把其它功能标为完成。

新增任务先写“解决什么问题、用户如何使用、完成如何判断、影响哪些模块”，再决定编号和实现。WG编号是项目标识，GitHub实际Issue编号由平台分配，可不相同。任务代码入口见[代码清单](./task-map.md)，公共修改规则见[协作方案](./collaboration.md)。
