# WG-06 管理权交接首片

规则来源：[首版规则](../11-首版成局加入与补位规则.md#发起人退出与管理权转让)与原 WG-06 Issue。此片只实现下列范围，不代表整张 Issue 或真实微信/数据库验收完成。

## 能做什么

- 当前唯一管理者从真实参加记录选择接任人，发起一份 pending 邀请；等待或拒绝均不交权。改选前先撤回，不能同时邀请多人竞争。
- 指定本人接受后才切换管理权；仅本人可拒绝，接受前当前管理者可撤回。接受后原管理者不能单方面反转，只能由现管理者重新发起。
- 没有自动过期或倒计时。报名截止不作为交接截止。
- 首片仅在接任者至少有一个**未取消、尚未开始、本人 joined 且已接受该段当前版本**的环节时允许新发起/接受。其它段已开始不一概禁止交接。
- 仅剩已开始/已结束或待重新接受的记录，本片未启用；这是实现范围，不宣称产品规则禁止。目标退出后 pending 保留，接受时资格不足则拒绝；仍可本人拒绝/当前管理者撤回，不自动改选接任人。这不确定后续完整终态策略。
- 交接不改变双方参加状态、席位、接受版本、活动链接、安排、待审批申请、费用、预订、核实或成局历史。原发起人退出不丢管理权；接任后也可按原规则退出参加并继续管理。
- 整场取消使尚未接受的交接失效；不把已转移管理权退回创建者，不自动退款、退订或通知。

## 权限、事务及恢复

新交接表保存来源管理版本，活动仍只有一个 `currentManagerId`。写操作统一 Activity 父锁与 Serializable 整笔重试；接受同时条件更新 pending 和管理归属/版本，不允许基于同一旧状态接受、撤回或旧管理者取消都成功。出错整笔回滚，不修改参加记录。

发起/撤回及既有管理写均先检查**当前管理者**再查原 key。接受/拒绝先验证活动与邀请指定本人，再识别原请求。已成功接受的原 key 只读历史邀请与当前权限：例如 A→B→C 后，B 重试旧 key 不会重新成为管理者；界面须区分“历史已接受”和“现在管理此活动”。未处理原 key 重试仍需当前资格和状态，不能称所有重试都只是只读。

相同 key 不同 body 冲突。创建原 key 定位最初邀请，不误拿后来另一份 pending。目标退出先则不能接受；接受先则之后退出不交还管理。新/旧取消服务只要写了 `cancelledAt` 都禁止接受，即使旧服务未更新新表，投影也不能假显示仍可接受。

客户端使用读取来源 session 和服务端 actor，不用昵称或候选参数授身份。确认前同步锁，最终 POST 前复验来源/版本/session/页面生命周期，并固定原 bearer。未知结果保留原 body/key，仅同一服务验证身份手动恢复；跨账号不恢复对方私人操作。已经发出的请求不能保证撤销，晚响应不修改新页面。

## 最小数据投影

仅当前管理者可得该活动候选；指定接任者只得自己的待接邀请，指定邀请历史仅其双方或当前管理者可读。候选按用户去重，仅含公开报名名及必要参加/环节标识；缺少公开名不从私人资料补齐。查询不读取 PrivateProfile、私人出发地、答卷或路线；公共分享入口不提供接任资格。当前完整名单读取上限为 2000 条 joined 参加记录（不是 2000 人）；超限整体报不可用，不截取后伪称完整名单。

`GET/POST /api/v1/activities/:activityId/handovers` 和 `GET/POST /.../handovers/:handoverId` 分别提供集合/指定邀请读取、发起及 accept/reject/withdraw。以共享严格契约及代码为准；响应携带原操作邀请当前状态与 actor 专属活动快照，而不是假成功布尔值。无匹配后端/迁移时应明确不可用，不使用普通邀请、内存状态或旧接口模拟交接。

## 迁移、部署和回退边界

第 10 条 additive migration 新增 ManagementHandover，保留既有管理归属；SQL partial unique 约束每活动最多一份 pending，另有来源/目标不同及状态时间约束。该部分索引由 SQL 维护，不声称 Prisma schema 自动表达了它。

**本片不执行生产迁移；第 9、10 条迁移均未真实数据库应用。SQL 静态检查、Prisma generate/validate、事务 fixture 不能证明真实 PostgreSQL partial unique 或锁并发已经通过。** 真实业务测试被原执行器权限限制阻塞，未换路径或重试绕过。最终本地检查以交付日志为准。

配套后端启用前必须由获准维护者确认目标、备份、迁移和统一服务版本。新后端整场取消也要在同事务更新待接交接，因此同样依赖第 10 条迁移；缺迁移不能跳过这一步并假成功取消。不能把仅导入小程序当作接口部署。禁止混跑新旧交接 writer 或重启旧无条件答卷覆盖服务。

回退源码至 v18 **不是数据库回滚**：关闭新交接入口，保留新表、邀请、事件、key、当前 currentManagerId/managementRevision；不 drop 历史、不恢复创建者管理权。v18 没有交接 UI，但既有管理写仍按 currentManagerId；其取消不更新新表，升级后仍须以 cancelledAt 判有效失效。任何数据迁移/修复须另行确认备份与授权，不盲目回放旧库。

## 获准独立环境的待执行验收

1. A 管理、B 已接受未来有效段；A 发起后仍是管理者；B 拒绝不交权。重新发起、撤回后旧邀请不可接任。
2. 重发给 B，B 接受；同活动权限变更，A 旧审批/核实/取消/需求管理写拒绝，B 可按现权限管理；双方席位和安排未改。
3. B 再交 C，B 用之前成功 key 恢复只读历史且不能重新获得管理权。不同 body 使用同 key 拒绝。
4. 分别验证接受/撤回、接受/取消、接受/本人退出的两种顺序；同活动不能同时存在两份 pending。
5. 接任者全部退出则 pending 仍在但不可接受，仍可拒绝/撤回；仅未定资格范围明确未启用。报名截止已过但目标合格段未开始仍可交接；等待锁跨开始重新检查。
6. 取消前已接受的归属不回退；取消的 pending 失效。仅旧取消 marker 情形也不可接任。
7. 未配置/404/畸形成功不显示交接成功；重复点击/取消/hide/unmount/账号切换/晚响应按[安全矩阵](write-boundary-matrix.md)核实际 headers、目标、body 与 key。

这些步骤是待执行真机/真实DB验收，不是本地 fixture 已替代通过记录。
