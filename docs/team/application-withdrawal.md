# WG-03：本人撤回整份待审批申请（前段最小范围）

原 Issue #3 明确包含申请、撤回、整体批准和拒绝；[首版规则](../11-首版成局加入与补位规则.md)明确申请不占位、增加环节不改变已有参加记录。本片补原缺失能力，不将其描述为修坏了原有撤回功能。

## 能做什么，不做什么

- 本人在活动详情查看自己的 pending 申请，确认列出的**整份环节组合**后撤回。不能只撤回一部分目标，不能管理者代他人撤回。
- 本片只启用活动及全部目标未取消、全部目标未到报名截止且尚未开始的情形。截止、开始、取消之后的新撤回规则尚未确认，前后端都明确**暂未启用**；这不是宣称用户决定禁止后期撤回。
- 撤回待审批申请**不是退出已加入环节**。已批准、已拒绝或已撤回的申请不能用新撤回命令改写；需要退出已加入席位时仍使用原独立退出功能。
- 已参加甲段、申请增加乙丙段时，撤回乙丙申请不改甲段席位、接受记录或任何安排。没有释放已参加席位、退款、费用重算、核实/预订变更或成局变更。
- 可重新申请仍开放且有位的环节，但必须使用新申请并接受当前安排、由管理者整体批准；旧申请键重放只能返回真实的已撤回状态，不复活旧申请或审批。

## 原子边界

`POST /api/v1/activities/:activityId/applications/:applicationId/withdraw` 仅接受 `expected_revision` 和 `idempotency_key`。身份来自已验证 session，不能从 body 传入 applicant 或管理权。路径 UUID 规范化，成功仍返回原 `ActivityDetail` 白名单投影。

服务使用原 Serializable 事务与父活动锁，与原审批在同一锁顺序下核对。锁后查询此活动内的**本人申请**，在旧键查找之前核对归属；外人/错活动/不存在不会泄露申请内容。新动作检查 pending、当前 activity revision、全部目标的完整性及范围；当前时间在锁和异步查询之后采样。

条件更新仍限定 `id + activityId + applicantUserId + pending`。只写申请状态及结束时间、activity revision、事件和成功幂等记录。不写 ApplicationTarget、Participation、安排/成员/主段版本、费用、核实、预订或成局字段。任何中途异常整笔回滚；可重试的事务冲突由原 mutation wrapper 整笔重新执行。

- 批准先提交：撤回冲突，不释放已批准席位。
- 撤回先提交：原批准不能再获得席位。
- 已成功原键重试：只返回当前真实快照，不重复写事件/版本；即使已进入后期也只是恢复既有结果。
- 相同键但不同语义：冲突。结果未知不等于“肯定未写入”；若首次未到服务端，原键重试仍会重新核对当前条件。

## 客户端恢复与隐私

确认前有同步锁，同屏其他写互斥。来源活动、本人 actor、session、申请及版本状态与页面 epoch 绑定；等待 `/me` 后在最终 transport 发送前再次同步检查。hide/unload/unmount 后不新发请求，已发请求不能保证撤销，晚结果不刷新另一页面或另一个账号。

原请求在发送前按活动及 actor 持久化。未知/畸形结果不显示成功；同一人重新验证后可手工重试原 body/key，不自动发送。其他账号不能继承旧私人申请或键。服务端已确认的业务冲突与未知传输结果区分；前者应刷新核对，不借旧输入覆盖新状态。

个人状态里的旧“重新接受功能尚未开放”文案同步改为查看安排版本审阅状态；[B1](arrangement-reaccept-b1.md)仍要求可信完整历史，最低人数 writer 尚未启用，不凭文案制造入口或历史。

## 实际验收层级

本片离线测试调用真实撤回服务、原申请/审批、原 Serializable mutation wrapper 与原快照投影；数据库为可回滚替身。测试覆盖两种执行次序、条件更新冲突、全回滚及整笔重试，**不是 PostgreSQL 真实并发证据**。组件/客户端回归覆盖确认、取消、重复、身份和生命周期、未知恢复及同屏正向。

无新表或迁移，未部署、未使用真实用户账号/真实数据库/微信原生。第 9 条 CAS 迁移实库与既有数据库业务验收仍保持原限制。本片不能关闭整张 WG-03，也不实现完整名册等其他原未完成项。

v16 源码和 dist 快照可回退；源码包回退不等于数据库回滚，更不能撤销已经发送的请求。回退旧源码也不应重新启用旧无条件答卷写服务。
