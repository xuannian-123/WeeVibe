# WG03：申请所用邀请入口的来源

## 本片做了什么

依据《首版成局加入与补位规则》第二节：组织者能看到由谁邀请及参加环节；公开入口只说明来源，不验证指定收件人或身份；邀请人退出不让既有入口失效。

本片从已交付 **v33** 独立副本实现，**不包含尚未完成独立末轮审阅的 QR 服务边界候选**。保持既定 demo 云登录与 cloud-http 公开配置。代码完成不代表目标后端或数据库已更新。

- 从带 `invitation_id` 的活动入口新申请时，原申请 body 增加可选 `invitation_source_id`。来源在服务端同一父活动锁/事务内核验属于当前活动，首次成功创建后原申请保存关联；不检查邀请人此刻仍参加，不额外授予席位。
- 不填来源的旧客户端请求与旧原键 body 原样兼容。申请、整份审批、接受版本、费用、席位、withdraw/退出逻辑不变。参与后仍通过原 `sourceApplicationId` 关联到申请，不新增私人资料复制。
- 新只读 `GET /api/v1/activities/:activityId/application-attributions` 使用同一 RepeatableRead 快照读取当前管理者权限及申请来源。管理者可见本活动全部申请，其他登录者只能看本人申请。每次最多完整读取 2000 份，超限为 503，不截成假全量。
- 展示的是该公开入口已发布的报名名，不读取邀请人的私有资料、生日、头像或出发地，不返回邀请人 userId。表中同名仍为独立申请，空名如实标未公开。
- `source:null` 表示未记录：可能是旧申请或未携带入口，**不能判断没有邀请人**。旧数据不推测、不回填。历史批准/拒绝/撤回申请保留原关联；它不是“谁实际转发链接”的证明。

## 协议、失败与原请求

新读取响应 `schema_version:1`，绑定 activity/revision、经过 `/me` 核验的页面 actor、当前管理者角色及可见申请 ID 完整集合。原 ActivityDetail 与 ActivityApplication 严格响应完全不加字段，不破坏旧客户端。

带来源的新申请须先成功读取支持归因的新接口；404/405、数据库缺迁移、坏 200 或版本不匹配不能当零记录，也不能静默去掉来源再提交。无来源的旧流程不因这一可选读取失败而停用。已经持久化的原申请可人工重试，不依赖新入口或当前归因读取可用；沿用**原 body、原幂等键、原来源**，不会追认当前新入口。

旧服务可能在查询幂等记录前以 HTTP 400 / INVALID_INPUT 拒绝新字段；带来源请求对此及 404/405 保留原键、显示结果未确认，不自动改为无来源请求。新服务在首次写前判定来源不适用时用统一 HTTP 409 / INVALID_INPUT，既不泄漏源是否存在，也不写申请；草稿保留。普通无来源错误策略不变。

页面来源/session/revision 的观察代次、hide/unload/unmount、最终 transport 前同步守卫与返回后守卫适用于带来源申请。观察到 A→B→A 不复活旧操作。正常同版时钟刷新不丢输入；换入口保留选择/昵称，但重新确认后才新提交。账号切换不带走旧私人草稿。已发送的写不能保证撤销；旧响应不得误确认新页面。

## 第11迁移与回退

`20261027040700_application_invitation_attribution` 仅增加：

1. `ActivityApplication.invitationSourceId` 可空 UUID；没有数据回填。
2. `InvitationSource(activityId,id)` 唯一索引和申请来源查询索引。
3. 同活动复合外键，`ON DELETE/UPDATE NO ACTION`；不能跨活动挂接、不能删来源抹历史。

本轮只做 Prisma 离线 generate/validate、SQL 静态核查及事务替身回归，**未连接或应用真实数据库**。第9/10/11迁移的目标库状态必须分别确认；不得把 schema 校验当迁移执行。生成客户端在独立副本内，原冻结版本的生成产物不变。

新版查询/写入要求完整匹配该迁移。新 Prisma 模型读取申请时也可能选择新增列，因此未应用第11迁移会使原无来源申请/详情读取失败；不能只禁用新 GET 就认为旧流程在新后端仍可用。发布前按[获准发布预检](authorized-release-preflight.md)在获准目标核迁移账本及实际 schema；预检旧示例侧重9/10，须另核本片列、索引、复合 FK，不能只看 health 或 ledger。先备份并确认恢复方案，不将本片授权理解成可连接/迁移任何数据库。

源码回退不等于数据库回滚；保留新列/约束/历史，不 drop、不回填、不改当前管理归属。旧服务可忽略可空关联，但不能承接新格式未知请求恢复或作为当前完整归因服务；部署客户端、服务器及schema须匹配，禁止用来源丢失的兼容降级冒充成功。

## 验收层级和最小步骤

作者 before：旧 schema 拒绝来源字段；实际申请 hook→原客户端发出的请求未包含来源。普通请求 control 正常。修后离线测试核来源绑定、旧请求/旧响应兼容、故障回滚、权限、同一原键恢复与页面迟回。准确数量和独立验证以本片最后冻结/验收记录为准。

获准匹配后端后，以两个真实微信账号（可同机切换）：A 创建公开邀请→B 从入口申请→A 在来源表核公开报名名和所选段→审批后检查席位与关联；A 退出后旧入口仍按原报名限制可用。检查转发不证明实际邀请人；旧记录显示未记录；其他账号不可读 B 的记录。断网未知结果改入口重试仍是同一原请求，旧后端失败不去来源重发。

以上微信、目标库复合外键/并发、后端联通均**尚未实际验收**；没有自动登录/发送邀请/订阅通知，没有真实二维码或身份审核扩展。
