# GO 本人活动发现与关系显示

## 修复范围

原账户接口仅查本人 `joined` 参加记录，导致管理者创建时不参加、只申请待审批、全部退出后无法从 GO 找回活动。本轮新增只读 `account.activity_records`，一场活动只有一张卡，允许重叠关系：

- 我在管理：当前 `currentManagerId` 等于认证用户，不要求本人占席位。
- 已参加：至少一条本人 `joined` 环节记录。
- 待审批：至少一份本人 `pending` 申请，不代表批准或获席位。
- 退出记录：至少一条本人当前 `exited` 环节记录；还有 joined 环节时标“部分环节已退出”。重新加入后按最新持久化关系显示，**不是完整历史审计日志**。

这只修活动回访和显示，不新增申请撤回、审批、管理转让、成局、重新接受或报名规则。仅浏览公开活动、收到链接、收藏地点或填写需求，不会被推断为参加/待审批关系。已保存邀请仍在独立的真实来源列表。

## 权限与兼容

查询 actor 来自已认证会话；请求参数中的 `user_id` 不决定返回账户。管理关系、参加关系和 pending 申请都按该 actor 限定，内部投影只选公开活动字段及本人状态字段。卡片不包含其他人姓名、申请、出发地点、答卷或个人资料。管理卡片也不新增读取成员私人数据的权限；后续业务操作仍须各自重新鉴权。

旧 `account.activities` 保持实际 joined 含义，不把管理、申请或退出混进去，以免旧客户端把它们当已参加。新客户端遇到缺少 `activity_records` 的旧后端，只回退已有 joined 列表，明确提示后端尚不支持完整管理/申请/退出记录，不能通过补假记录掩盖。

## 日期与显示

关系标签与时间阶段分开。真实 joined 的未来卡片为“待参加”，没有 joined 的管理/待审批/退出卡片只写“未开始”；进行中与已结束按服务器时间计算。已取消/本人参加环节已取消单独说明，不伪装正常结束、批准或参加。

日期明确按活动 IANA 时区格式化并标注实际格式化时区，不用设备本地时间冒充活动时区。设备 Intl 不支持时明确显示 UTC 回退。已有本人 joined 环节时沿用本人参加环节的时间范围；否则明确显示活动整体时间。去重后，活动中在前，待开始按时间近到远，结束历史按结束时间新到旧；相同时间以活动 ID 稳定排序。范围仍有上限：最多最近创建的 100 条相关活动，不声称无限历史已全部加载。

## 本轮证据与限制

修复前真实调用 `accountSnapshot` 的 Prisma 查询替身用例失败：3 个应回访活动全部缺失；修复后服务查询与首页组件用例通过。测试替身遵从实际 where/select，覆盖认证身份来源、他人记录排除、重叠去重、时间边界/取消、旧后端提示、卡片导航和退出登录清屏。

这不是实际 PostgreSQL 或微信真机验收；没有新数据库迁移，没有连接共享库、真实用户数据、付费供应商或部署后端。新的源码和构建不会自动更新用户当前连接的旧 API。最终测试/构建以本轮交付日志为准。
