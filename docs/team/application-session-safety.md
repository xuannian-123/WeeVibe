# 申请与审批的显示身份绑定

## 修复前证据

实际 `useApplications`、`useStoredWrite` 与 API client 的离线探针显示：页面仍是 A 的活动快照，当前令牌换成 B 时，旧申请选择/昵称会带 B bearer 发出 POST；旧审批意图也会如此。另一个探针确认换成 B 的有效活动快照后，A 未提交的昵称和选择还残留在表单。不是服务器允许 A 越权，而是客户端把 A 的意图错误交给了 B。

## 当前边界

- `useActivityDetail` 把已通过会话核对的读取快照 session 传给申请 hook；不从表单挂载时的当前 token 推测来源。
- 新 `applications/api.ts` 先检查来源会话、通过该会话的 `/me` 核对 actor。每次最终 transport 调用前再次同步核对，会话检查与调用之间无 `await`。
- 请求 Authorization 固定使用原预期 session，不在身份验证后改用新 token。响应后再次检查会话，沿用原 ActivityDetail schema，并核对稳定的 activity ID 与 viewer actor。
- 本地未提交表单按活动+actor 隔离；换活动或身份立即隐藏旧值并清理该表单状态。同一 actor 普通刷新保留输入；活动版本变化后仍须重新接受当前安排，不能靠旧 consent 静默提交。
- 原待确认请求存储键、幂等键、选择及昵称不变。B 不能恢复或重试 A 的原请求；重新验证为 A 后可沿用原请求。缺失/切换会话及未知响应保留原待确认操作，不冒称已提交。
- 申请、全部批准/拒绝、席位、截止、取消、重试与权限判定仍由原服务器规则决定；此客户端绑定不是新的授权来源，也不增加撤回或放宽审批。

## 验证范围

新增回归覆盖实际 headers/payload、切换前/身份读取中/最终发送前/晚返回、旧用户输入隐藏、同人刷新与新版本 consent、重复点击、未知结果、同 actor 新 session 的原键恢复、取消/安排过期/满员错误、批准/拒绝与严格请求 schema。独立审计另行验证。

真实请求如果已在 A 身份下发出，切账号不能撤销服务器操作；客户端只拒绝把晚返回当作当前账号的确认，需要回到 A 刷新核对。离线替身测试不是真实 PostgreSQL 事务或微信原生验收；无后端、数据库迁移、配置或部署变化。

## 已记录、未混入本补丁

v10 当时记录了退出/晚到确认框重复点击和卸载后继续发送的三项失败，未混入申请身份补丁。后续独立修复与新增最终 POST 前生命周期检查见 [退出 / 晚到确认安全](participation-confirmation-safety.md)。历史三项失败不代表该后续修复后的当前状态；完整活动闭环仍不能据此宣称完成。
