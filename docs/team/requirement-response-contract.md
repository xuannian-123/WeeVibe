# 需求成功响应的运行时校验

## 修复事实

此前需求客户端仅把 HTTP 2xx 对象强制转换成 TypeScript 类型。不兼容服务返回 `{ "ok": true }` 时，创建表单会调用 `saved`，随后因缺少 `viewer` 崩溃。独立 React 探针在修复前复现了 `saved_calls: 1 / FORM_CRASH`，修复后通过。

`platform/requirements-api.ts` 现在是需求列表、按活动查询、详情、草稿创建/保存/发布、答卷保存/恢复、截止和定案的成功数据边界。使用现有 Zod，无新依赖；不改失败响应解释、服务端业务规则或数据库。

- 成功响应必须满足对应形状；详情返回的 collection ID、按活动查询的 activity ID 必须匹配目标；创建返回必须匹配请求 kind/activity_id。UUID 比较忽略大小写，不误拒服务端小写规范化。幂等创建重放允许返回已更新的版本/状态，不要求与初始草稿内容相同。
- 缺字段、错类型、未知状态或缺少已保存答卷的 CAS 版本返回 `INVALID_RESPONSE`，表示结果未知，**不表示服务器肯定没写入**。不调用保存/更新回调，不用损坏数据替换旧表单。
- 创建未知结果沿用原编辑器的原幂等键和请求。答卷继续使用既有版本冲突流程，不把一次未知结果当幂等成功。
- 错误只显示固定可恢复提示，不输出原始 JSON、私有字段或 Zod 路径/诊断。
- 允许可选 `organizer_avatar` 缺失；未完成草稿的空日期仍合法。不重新执行发布业务校验，也不伪造默认答卷版本。
- 输出对象的未知附加字段被剥除；复用的严格嵌套输入结构如答案、题目、地点等若不兼容会拒绝整个响应。未知字段不会透传进组件状态。客户端过滤是纵深防护，不能代替服务端的权限与隐私投影。
- 旧后端已有答卷缺 `response_version` 时明确提示版本不匹配，不降级到无 CAS 写入。需要部署匹配前后端，不是重新登录就能修复的错误。
- 初次读取失败不再同时断言“这场活动尚未开放需求收集”；只有服务端明确返回 `{collection:null}` 才进入未开放分支。

## 验证与限制

新增成功契约、实际 React 创建/管理命令/答卷及读取错误回归。包括旧合法可选字段、缺字段/错类型、未知字段、私有 sentinel、同键重试、切账号、合法重试和明确空结果。完整离线测试、类型与双端构建以本轮交付日志为准。

本次没有真实微信、数据库业务并发、部署或地图/模型调用。成功数据结构通过不证明后端实现正确；当前编辑器的恢复也不是跨关闭/重启持久化。回退仅涉及客户端代码；无需数据库回退，但恢复旧客户端会恢复本缺陷。
