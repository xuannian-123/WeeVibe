# 朋友出游首屏 · 活动安排与其他明细专项核对

> 历史记录，本轮两张首屏卡及朋友对应编辑页已经移除；当前以[单一整理入口与依赖清理](friend-intake-20261030.md)为准。本文的时间／人数／公开费用规则仍解释历史记录和团建的真实依赖，但旧朋友入口、跨页回跳、两个 options 预览脚本及当时测试数字不再代表当前实现。旧可操作页面已跳转新版，旧可执行产物已清除。

2026-10-30。本轮只核对朋友出游首屏两张选填卡及其保存、最终创建、筹备展示、生成与定案衔接。继续当前 C 风格，保留原三卡入口及最后一步发起；小橘头问答、解析和模型调用顺序保持。

## 已修正

- 活动安排说明时间与地点的作用：日期是当前候选的日期锚点，开始时间是首环节开始条件，结束时间是最晚结束边界；未标记确定的日期显示为暂定，不等同于全员接受。
- 改偏好日期后，若原结束日期／跨天时段不再合法，进入最终预览前带回活动安排并显示具体原因。跨字段尚未完成的本机草稿仍保留名称、时间、地点及费用，不能因整份 schema 的关系校验失败而清空原内容；正式保存／创建仍执行完整校验。
- 编辑人数、费用只更新该 section 的确定项，不再把未勾选日期或其他 section 的内容一起提升为确定。日期确定性仍按本人偏好确认处理。
- minimum 文案改为人数意向，说明不会按人数自动成局；所有当前成员明确确认后可以完成筹备定案，不新增正式活动最低人数门槛。
- capacity 明确是筹备填写人数上限，包含局头。编辑页按已知成员数阻止不合法降低；后端在持有活动锁后核对真实成员总数，包含未提交者，拒绝低于当前人数的新上限，不删除原成员。
- 朋友原本最多能加入 500 人、生成却只支持 50 人，且没有移除成员入口，会造成收齐后无法继续。本轮将新建／修改的朋友人数范围与新增加入的系统上限统一为共享常量 50；自设更小 capacity 继续生效，留空采用系统上限。团建保留 500。旧超范围记录仍保留、可读取及保存已有成员答卷；超范围推荐只作明确不可生成提示，不提供不存在的“调整人数”入口。
- 筹备满员的新访客不再先进入偏好填写或自动发起加入；已有成员仍可保存本人答卷，不重复计数。
- 人数原始输入拒绝指数、十六进制、分数和超范围数据；参考金额允许 0，最多两位小数，不把空白当 0、不把未知口径当免费。
- 公开费用以发起人的参考单独展示在筹备、候选、完整安排及定案页面，保留金额／口径／说明；没有传给 AI 核价，也不替代各环节“费用待核实”。个人预算及出发地仍只在本人填写查看。
- 修改公开费用仍参与现有来源指纹，使旧候选失效，继续要求按原流程重新生成／确认；不绕过版本或幂等边界。
- 保存遇到服务端人数变化时，编辑页展示后端实际人数原因并保留输入，不报告成功。

## 实现范围与环境

新增 details-validation、details-summary、public-details 组件和样式，接入原 Designer、DetailsEditor、Manage、Review、Workflow 与 FinalResult。复用原 GET／POST gathering、details、generate、workflow 契约，不新增端点、状态表或迁移；contracts 只增加共用朋友人数常量，通用 details schema 仍支持团建范围。

后端修改位于 gatherings/service.ts 的条件与加入校验、generation.ts 的共用限制常量。**这些新后端规则目前仅在本地源码中，更新对应共享后端后才会对共享环境生效。**没有部署、改库、生成微信预览码、上传或替换体验版。
