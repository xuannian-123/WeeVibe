# 成员首次开发条件预检

这份清单由成员的Codex在首次接手、换电脑或连接/依赖变化时执行。目的在于明确这台电脑能做什么、尚缺什么，不重新验证维护者已经完成的整套业务。仅查看本机配置时只报告是否存在/有效，不输出密钥、数据库连接或会话。

## 先选本次开发路径

| 路径 | 可以怎样开始 | 还不能据此宣称什么 |
|---|---|---|
| 页面、交互、调用现有接口 | 本地分支构建小程序，显式连接当前共享演示API | 自己尚未部署的新接口不会在共享API生效 |
| 新后端、业务规则、数据库、AI能力 | 本机或独立开发后端＋独立开发库；按改动配置服务端供应商 | 不得默认使用共享演示库做迁移，也不能把小程序已登录当成本机后端已具备可信身份入口 |
| 纯函数、契约和规则逻辑 | 本机依赖与相关离线测试，可先不连接微信/数据库/供应商 | fixture和离线通过不等于完整联调或手机结果 |

根据任务只检查相关条件。例如页面开发不要求每人都准备数据库和模型Key；缺手机资格也不妨碍先写代码、做离线检查。

## 本机检查与补齐

在实际克隆目录执行，不能照抄维护者电脑的绝对路径：

```text
git rev-parse --show-toplevel
git status --short --branch
git remote -v
node --version
pnpm --version
```

- 仓库对应`xuannian-123/WeeVibe`；从已同步的main创建自己的功能分支。存在别人的未提交修改时保留，不自动stash、reset或切走其分支。
- 要求Node ≥24.11且<25、pnpm 11.15.1。先检查现有运行时，不无故重装或升级依赖。
- 首次缺依赖时运行`pnpm install --frozen-lockfile`。需要API/全工程类型检查且缺Prisma产物时运行`pnpm db:generate`，这是离线代码生成，不连接数据库。
- 只有涉及登录函数或需跑对应测试时，才补`npm ci --prefix cloudfunctions/weevibeLogin --ignore-scripts --no-audit --no-fund`。
- GitHub写操作前再确认自己的实际账号、目标仓库及分支写权限；fork协作需要选择自己的fork。队员不必登录维护者账号，也不索取维护者GitHub凭据。

## 页面与现有演示接口

```text
pnpm build:mini:demo
```

此命令显式读取仓库内`config/miniprogram-demo.json`的五个公开客户端字段，构建连接当前演示云登录和HTTP函数的小程序。它不读取后端.env，不上传源码、不部署、不生成二维码、不替换体验版；配置检查可单独运行`node scripts/build-mini-demo.mjs --check`。

公开环境ID、AppID和函数名不是密钥，不授管理权限或微信成员资格。默认的`pnpm build:mini`仍使用调用进程配置；无连接配置时它也可能编译成功，因此不能把普通构建成功写成“可以联调”。

构建后由微信开发者工具导入`apps/miniprogram`，使用仓库project.config.json中的AppID及基础库要求，保持urlCheck=true。检查工具安装、登录以及本人是否被管理员添加为相应开发/体验成员；这些条件必须在成员自己的账号下实际确认，Codex不能从源码推断已获权限。

在工具中打开首页/创建页并实际点击微信登录，确认真实接口可读、能打开已有页面。需要AI或高德功能时，再用少量相关请求核对，留意现有额度和限流；不为自检自动生成活动、申请或批准。共享演示API上的业务写入会产生共享数据，实际测试按团队约定标识。

手机预览还需开发工具实际生成本分支的新二维码，并由有资格的微信扫码；旧二维码不会因本地改代码而更新。未做手机操作就写“待实际验证”，不要清理原会话/草稿来制造新环境，必要时使用独立项目缓存。

## 新后端与数据库

1. 先明确对应API地址、运行位置和数据库归属。优先本机或专用开发环境；没有分配好时向维护者说明具体缺口，不覆盖现有演示函数。
2. `apps/web/.env.local`只放这份开发后端的服务端配置，且不入仓。不复制维护者整份.env，不把共享演示库连接当作默认开发库。
3. 核实独立开发库、迁移目标及本次改动，再按[开发指南](./development.md)启动API。本机代码生成与迁移是不同操作；不能用`db:migrate`作为通用环境探针。
4. 确认可信微信登录方式能到达这份开发后端。当前云登录函数的签名入口固定指向共享演示API，不能假定把客户端API地址改为localhost就能复用同一身份链路。手机上的localhost也不是开发电脑；需要HTTPS入口和独立登录接入时由维护者协调，不改原登录函数或重置旧AppSecret。
5. 通过本机服务的health、ready及相关身份/业务接口分别验证：health只证明进程，ready只证明对应就绪条件，均不代表完整微信业务成功。可以先做离线规则和接口测试，但fixture结果单列。
6. 新模型或地图服务调用只在对应开发服务端配置必要Key；现有演示API已经持有自己的配置。不要让成员把供应商Key放进小程序，或认为本机Key会自动同步到云端。

目前没有自动为每个分支部署隔离后端/数据库的流程，也没有PR自动预览。依赖这类环境的任务应在开始时提出，由维护者安排；开发者继续先推进契约、离线逻辑和可独立预览的界面。

## Codex必须给出的检查结果

首次检查后，用简短表格向成员反馈。按实际观察填写，未检查就是待验证：

| 检查项 | 状态 | 证据或下一步 |
|---|---|---|
| 实际仓库、分支与现有修改 | 通过/缺少/待验证 | 当前目录、分支，是否需要先保护现有改动 |
| Node、pnpm与项目依赖 | 通过/缺少/待验证 | 实际版本及必要安装结果 |
| 本分支小程序构建和连接配置 | 通过/缺少/待验证/不涉及 | 使用的命令与目标，不能只写“build成功” |
| 开发工具、微信资格和实际登录 | 通过/缺少/待验证/不涉及 | 实际操作结果，缺权限时列出需要管理员添加的资格 |
| 本次接口对应的后端与开发库 | 通过/缺少/待验证/不涉及 | 是现有演示API还是独立开发后端，是否包含本分支修改；不输出连接串 |
| AI/高德能力 | 通过/缺少/待验证/不涉及 | 使用已部署接口还是本机Provider；真实调用与离线样例分开 |
| 手机新预览 | 通过/缺少/待验证/不涉及 | 是否实际生成并扫码，不能套用维护者的既有结果 |

最后明确：**现在能开始哪些工作；哪些完整流程还不能验证；需要成员本人或维护者补什么。** 不把条件缺失误报成代码故障，也不因此停止所有可独立推进的工作。后续只重查变化的条件，不反复执行已通过的双微信基础验收。
