# 局长的决策逻辑 · 设计稿

> 局长是一个**组织者 + 决策者**：你可以用任何方式跟它说你的情况，它听懂之后，替一群人做出**尽量照顾到每个人**的决定；
> 没有完美答案的时候，它不会硬选一个让某人吃亏的方案了事，而是**找出卡在哪里，提出代价最小的解决办法，并且亲自去协调**。

本文只讲"怎么想"，不讲界面细节。和现有代码的关系见第 10 节。

---

## 0. 设计原则

1. **先听懂，再决定。** 所有输入（私聊、按钮、截图、刷卡、档案）最后都变成同一种东西：**需求（Need）**。决策只看需求，不看输入方式。
2. **硬的不碰，软的权衡。** 门禁、清真、主角必须到，是硬约束，方案不能违反；"想早点回""不想跑太远"是软偏好，有强弱，可以权衡。
3. **先保底，再求好。** 排序准则是"先让尽量多的人被照顾到 → 再让最吃亏的那个人少吃亏 → 最后让大家整体更满意"。不靠一个看不懂的总分。
4. **没有完美解时，找最小的让步。** 让步只问愿意让步的人，而且轮流问，不总让同一个人让。
5. **拍板交给代码，理解和表达交给大模型。** 决策可复算、可解释；大模型听不懂时降级到规则，并且**硬约束必须本人确认过才当真**。
6. **隐私是前提。** 一切公开输出只用聚合结论（沿用防火墙和反事实检验）。

## 1. 局长要决定什么

| 决策 | 说明 | 现在 |
|---|---|---|
| 什么时候 | 候选日期 × 开始时间 | 有 |
| 在哪 | 公平集合点附近的真实场地 | 有 |
| 谁能来、待多久 | 结果，不是变量：由时间和通勤算出 | 有 |
| 玩什么 / 吃什么 | 发起人没定品类时，由局长按大家的偏好定 | 没有（第二期） |
| 怎么坐 | 局内编排 | 有（v4） |
| 怎么修复冲突 | 加候选时间、私下请人让步、拆场、换品类、分账方式 | **没有，本稿重点** |

## 2. 输入：统一的需求模型

### 2.1 多种互动方式

| 方式 | 例子 | 变成什么 |
|---|---|---|
| 自然语言私聊 | "我 7 点下班，宿舍 11 点门禁""最近手头紧""腿受伤了不想走太远" | 大模型抽取 → Need，规则兜底 |
| 快捷组件 | 时间选择、预算滑块、忌口勾选 | 直接是结构化 Need（置信度 1） |
| 截图 | 课表、群聊截图 | 多模态解析 → 时间类 Need |
| 刷卡 / 投票 | 右滑想去、左滑不想去 | 品类 / 场地偏好 Need |
| 档案记忆 | 上次的预算、常用时间、口味 | 预填 Need（标"局长猜的"，本人可改） |
| 协商回复 | 局长私下问"晚 20 分钟到可以吗"，回答"可以" | 修改已有 Need（见第 5 节） |

### 2.2 Need 的结构

```ts
type Need = {
  id: string;
  memberId: string;
  dim: "time" | "travel" | "money" | "food" | "activity" | "ambience" | "people" | "body" | "join";
  kind: "hard" | "soft";
  strength: 1 | 2 | 3;        // 软偏好的强弱：1 随口一提 / 2 在意 / 3 很在意
  rule: NeedRule;             // 可计算的参数，见 2.3
  source: "chat" | "widget" | "screenshot" | "swipe" | "profile" | "negotiation";
  evidence?: string;          // 原话，只在本人视图出现
  confirmed: boolean;         // 本人确认过（组件输入天然为真；大模型推断的硬约束必须回问确认）
  confidence: number;         // 0–1
};
```

### 2.3 维度表（每一维都要能"算"）

| 维度 | 硬约束例子 | 软偏好例子 | 怎么算 |
|---|---|---|---|
| time 时间 | 那天来不了；门禁 23:00 | 想早点回；周六最好 | 到达 / 离开时刻 → 能否到场、待多久 |
| travel 通勤 | 单程不能超过 60 分钟 | 不想跑太远；想坐地铁 | 每人到每家店的通勤分钟（按交通方式） |
| money 花费 | **不设硬约束**（见第 9 节） | 人均 80 以内（强度 1–3） | 人均价 vs 上限，超得越多扣得越多 |
| food 饮食 | 清真、素食、过敏 | 不吃辣、想清淡 | 场地类型 / 菜系 / 是否有鸳鸯锅 |
| activity 玩什么 | — | 想吃烤肉；不想 KTV | 刷卡表态、品类匹配 |
| ambience 环境 | 不能有烟 | 想安静能聊天；不想喝酒 | 场地属性（可能未知，见 2.4） |
| people 人 | 主角必须到 | 想认识谁；不想和谁坐 | 到场 / 排座（v4） |
| body 身体 | 不能爬楼梯 | 腿伤不想走太远 | 步行距离、楼层（可能未知） |
| join 参与意愿 | 一定要来（主角） | 想来 / 随缘 | 来不了时有多失望（见 3.2） |

### 2.4 听懂的规则

- **大模型推断出的硬约束必须回问确认**："确认一下：23:00 前必须回去，是硬性的吗？"（快捷回复"对，必须 / 不是，尽量就行"）。**确认之前按硬约束算**：两种错误的代价不对称，把门禁当成软偏好可能把人排到门禁之后，那比多问一句糟得多。回答"不是"就降成软偏好（门禁 → "想几点前结束"，强度 2；"最多一小时" → 强度 3 的软偏好）。组件里亲手选的不回问。（已实现：`intake.ts` 的 `hardToConfirm` / `resolveConfirm`）
- **场地属性不确定时如实说**：高德只给评分、人均、类型。"安不安静""能不能抽烟"多数情况不知道，按"不确定"轻扣分，并在本人解释里写明"这家安不安静不确定"，绝不编造。
- **能落到规则的就落到规则**："腿受伤了不想走太远" → body：步行 ≤ 500 米，强度 3；"想早点回去追剧" → time：离开 ≤ 21:30，强度 1。抽不出参数的需求保留原话，仍然给本人看，但如实说"这条局长没法算进去"。

## 3. 每个人的满意度：可解释的扣分制

### 3.1 计算

对每个候选方案 c（时间 × 场地）和每个人 i：

1. **能不能来**：时间和硬约束都满足才能到场；任何一条硬约束不满足 = 来不了。
2. **满意度** u(i, c) = 100 − Σ 每条软偏好的扣分。每条的扣分 = 强度系数 × 违反程度（0–1）× 维度上限：

   | 强度 | 系数 |
   |---|---|
   | 1 随口一提 | 0.4 |
   | 2 在意 | 1.0 |
   | 3 很在意 | 1.8 |

   例："人均 80 以内（强度 3）"，这家人均 104，超 30% → 违反程度 0.5 → 扣 1.8 × 0.5 × 40 = 36 分。
3. **每一分扣在哪都记下来**，变成给本人的解释："你说手头紧，这家人均 104，扣分最多的就是这一条"。

现有的通勤、迟到、早走、当天意愿扣分保留，作为 time / travel 维度的默认软偏好。

### 3.2 来不了怎么算

来不了的人满意度不是一律 0，取决于参与意愿：

| 参与意愿 | 来不了时的满意度 |
|---|---|
| 一定要来 / 主角 | 不允许（主角来不了的方案直接否决） |
| 想来（默认） | 0 |
| 随缘 | 40 |

这样"随缘"的人不会和"很想来"的人挤占同样的照顾优先级。

### 3.3 "被照顾到"的定义

一个人在方案 c 里**被照顾到** = 能到场 + 硬约束全部满足 + 满意度 ≥ **50**（保底线）。
这是对外讲得清的一句话："这个方案照顾到了 9/10 的人"。

## 4. 怎么选：先保底，再求好

对所有候选方案按下面三级准则排序，前一级分不出高下才看下一级：

1. **照顾到的人最多**（主角没被照顾到 = 否决）。人数相同时，按公平账本加权：之前吃亏多的人被照顾到，算得多一点。
2. **最吃亏的人损失最小**：比较每人的加权损失 w_i × (100 − u_i)，先比最大的那个，再比第二大的（leximin）。差距在 1 分以内视为打平，避免为了零点几分牺牲整体（不能更大：大家都还不错时满意度挤在 85–99，容差太大会把公平账本的作用吞掉，这是用演示场景测出来的）。
3. **整体最满意**：Σ log(1 + u_i)（纳什福利）。它天然偏好"大家都还不错"，而不是"几个人特别爽、几个人一般"。

**这套准则的一个直接后果**（团队要心里有数）：只要不把别人拖到保底线以下，局长会为了照顾到最后一个人，让大家各让一点——比如为一个预算紧的朋友选一家更便宜、但大家多走 15 分钟的店。这正是"尽可能照顾到每个人"；反过来，如果照顾这一个人会让别人掉到保底线以下，第一级准则自然不会选它。

为什么不用一个总分：总分里的权重谁都说不清。三级准则每一级都能用一句人话解释，评委问"凭什么选这个"，可以直接念。

**备选方案**沿用现在的做法：在帕累托前沿上挑 2–3 个有实质差异的方案（人最全 / 最省钱 / 大家最舒服），让大家投票。局长的推荐 = 上面三级准则的第一名。

**跨局公平账本**沿用，并新增一笔"让步账"：谁在协商里让过步，下次被问到的优先级降低（见 5.3）。

## 5. 极端情况：诊断 → 修复 → 协商

这是局长和普通工具的分界线。

### 5.1 什么时候触发

推荐方案出来后，出现下面任一情况就进入修复流程：

| 触发 | 例子 |
|---|---|
| T1 有想来的人来不了 | 小王 20:00 才能到，候选都是 18:30 开始 |
| T2 有人掉到保底线以下 | 两人私下预算 60，发起人定人均 150 |
| T3 主角在所有候选里都来不了 | 生日局，寿星周五加班 |
| T4 硬约束和品类冲突 | 火锅局有清真的朋友，附近没有清真火锅 |
| T5 照顾到的人不足一半 | 时间极度分散 |

### 5.2 诊断：卡在哪

对推荐方案，找出没被照顾到的每个人是被哪几条需求卡住的。然后检查，如果放宽其中一条，这个人能不能被照顾到。

- 只给发起人看**聚合结论**："有 2 位朋友的时间凑不上，都卡在开始时间太早"。
- 被卡住的本人私下看到具体原因："你 20:00 才能到，这几个方案都是 18:30 开始"。

### 5.3 修复菜单：按代价从小到大

| # | 修复办法 | 适用 | 局长怎么做 | 代价 |
|---|---|---|---|---|
| R1 | **私下请灵活的人让一小步** | T1 T2 | 例："有位朋友 7 点后才能到，开始时间改到 19:30，你可以吗？"只问灵活的人（他们在这一维上是软偏好），按"让步账"轮流问 | 最小 |
| R2 | **私下请被卡住的人自己松一点** | T1 | 例："这次你只能待 40 分钟左右，还来吗？"或"晚到 20 分钟可以吗？"绝不请人违反门禁、清真这类硬约束 | 小 |
| R3 | **加一个候选时间** | T1 T3 T5 | 找出能照顾到最多人的新时段，一键私下问一圈"周日下午行吗？"；主角的时间优先问 | 中 |
| R4 | **换一种做法** | T2 T4 | 预算悬殊 → 换人均更低的店，或者"按点的菜分账，预算紧的朋友少摊"（复用小票分账）；清真冲突 → 扩大半径找清真店，或换成清真菜系 | 中 |
| R5 | **拆成两段** | T1 | 例："晚到的朋友直接来第二段桌游"；只在品类允许分段时提 | 较大 |
| R6 | **接受有人来不了 + 补偿** | 都修不了 | 私下告诉他"这次没照顾到你，下次你优先"，并记进账本，下次权重更高 | 最后手段 |

**怎么挑修复办法**：对每个候选方案，算出"要让它照顾到所有想来的人，最少需要哪些让步"，每个让步有代价：

- 代价 = 让步的大小 × 让步人的权重；
- 最近让过步的人权重更高，所以越不容易再被问到；
- 硬约束的让步代价为无穷大，也就是不可能。

选总代价最小的"方案 + 让步组合"。人数不多（≤ 30 人、≤ 3 处让步），可以直接枚举，结果确定、可复算。

### 5.4 协商闭环：局长自己去问

1. 局长私下给要问的人发一条**是 / 否**询问（站内信 + 私聊里的快捷按钮）。每个人每局最多被问 2 次。
2. 对方点"可以" → 他的 Need 被更新（source = negotiation）→ 自动重算 → 群里只说"局长私下协调了一下，现在所有人都能来了"。
3. 对方点"不行"或超时 → 换代价第二小的组合，继续问。
4. 都不行 → 把 R3–R6 的建议交给发起人一键决定。

**隐私**：
- 被问的人只知道"有位朋友卡在 X 上"（聚合说法，和现有规则一致），不知道是谁。
- 别人不知道谁被问过、谁答应了。
- 协商同样走攒批重算，不能从"方案什么时候变了"反推出是谁答应的。

### 5.5 一个完整例子

> 摄影社 8 人，周五晚。小王 20:00 才能到（加班）；小李 21:30 前必须回宿舍（门禁，硬约束，已确认）；其余人 18:30 以后都行。候选：18:30 / 19:00 / 19:30 开始。
>
> - 18:30：小王晚到 90 分钟 → 来不了。19:30：小王晚到 30 分钟，小李 21:05 得走 → 两人都能来，但小李只待 95 分钟、小王晚到。
> - 推荐 19:30：照顾到 8/8，最吃亏的是小王（晚到）。
> - 如果小李的门禁是 20:30（20:05 就得走）：18:30 开始小王晚到 90 分钟来不了；19:30 开始小李只能待 35 分钟，不到 60 分钟也算来不了 → 每个时间都少一个人，触发 T1。
>   - 局长诊断：卡在"开始时间"和"门禁"之间。门禁是硬约束，不能请小李晚回。
>   - R2：私下问小李"这次 19:30 开始，你大约只能待 35 分钟，还来吗？"（松的是"至少待满 60 分钟"这条软偏好，不是门禁）。小李说可以 → 两人都能来。
>   - 小李说不行 → R3：私下问一圈"周六下午行吗？"7 人可以，加上周六 15:00 → 照顾到 8/8。
>   - 群里只看到："局长私下协调了一下，加了周六下午的候选，现在所有人都能来。"

## 6. 外部因素：天气、营业时间、交通、排队、订位

人的需求之外，还有一类所有人共享的**公开事实**。它们不涉及隐私，但会让一个"算出来很完美"的方案在现场翻车。

### 6.1 数据从哪来（都已实测）

| 因素 | 来源 | 能拿到什么 | 拿不到什么 |
|---|---|---|---|
| 天气 | 高德天气接口（现有 key） | 今天起 4 天；白天 / 夜间各一条：天气现象、温度、风向风力 | 降水概率、逐小时预报、空气质量；4 天以后的预报 |
| 营业时间 | 高德场地搜索 `open_time` | 如"11:00-21:30"，有的分多段、有的缺失 | 节假日临时调整（偶尔写在 `opentime2` 里） |
| 室内 / 户外 | 楼层字段（B1、3F 等）+ 场地类型 | 有楼层 = 在楼里；公园、景区、露营、室外球场 = 户外 | 室外球场和室内球馆有时分不清 |
| 通勤 | 高德距离 / 公交路线接口 | 每人到每店的分钟数 | 实时晚高峰（只能按时段估） |
| 排队 | 现有规则：饭点 + 高分店 | 粗略估计 | 实时排队 |
| 订位 | 人数 + 店型 | "8 人以上建议订包间 / 大桌" | 店里是否还有位 |

结论：天气只能做到"白天 / 夜间、会不会下雨、冷不冷热不热"这个粒度，**而且只在 4 天内有效**。设计必须诚实地接受这一点。

### 6.2 外部因素怎么进入决策：四种作用方式

| 作用方式 | 含义 | 例子 |
|---|---|---|
| **硬过滤** | 方案直接不成立 | 店 21:30 打烊，但方案 19:30 开始、要玩 2.5 小时 → 这个"时间 × 店"组合不成立；户外烧烤 + 当晚大雨 / 雷阵雨 → 不成立 |
| **软扣分** | 所有人的满意度一起降 | 下雨 → 步行段长的店扣分、通勤时间 +20%；气温 ≥ 33℃ → 户外扣分；太晚结束 → 扣分 |
| **风险 + 备案** | 方案成立，但有翻车可能，提前准备 B 计划 | 4 天外没有预报、但选的是户外 → 自动同时挑一个室内备选；当天"小雨" → 写进风险，附上备案 |
| **提醒** | 不影响选哪个，但要告诉大家 | 带伞、加衣、提前 10 分钟出发、店 21:30 打烊别太晚点单 |

**它和个人需求叠加时只进本人那份**：比如下雨 + 某人私下说"腿受伤不想走太远"，扣分和解释只出现在那个人自己的视图里。天气本身是公开的。

### 6.3 天气的具体规则

| 天气（预报的对应时段） | 户外场地 | 室内场地 | 通勤 | 提醒 |
|---|---|---|---|---|
| 晴 / 多云 / 阴 | 正常 | 正常 | 正常 | — |
| 小雨 / 阵雨 | 扣分，并准备室内备案 | 正常 | +15%，长步行段扣分 | 带伞 |
| 中雨及以上 / 雷阵雨 / 雪 | **不成立** | 正常 | +25% | 带伞、提前出发、注意回程打车难 |
| ≥ 33℃ | 扣分 | 正常 | — | 防暑 |
| ≤ 5℃ | 扣分 | 正常 | — | 加衣 |
| 风力 ≥ 6 级 | 扣分 | 正常 | — | — |
| 4 天外没有预报 | 视为未知：户外方案**必须带室内备案** | 正常 | 正常 | "前一天局长再确认天气" |

### 6.4 天气会变：定局后的复查

定局不是终点。定时任务（现有的 30 秒巡检）在**活动前 24 小时**和**前 3 小时**各拉一次预报：

- 风险没变 → 不打扰。
- 风险升级（比如变成中雨），且方案带了备案 → 给发起人一键"切到备案"；如果大家定局时就同意了"下雨自动换"，就直接切换，走现有的稳定重规划（#12），给每个人发变更私信。
- 风险升级，但没有备案 → 立刻找一个室内备选，交给发起人确认。
- 不管变没变，前 3 小时那次都会把天气写进"出发提醒"（带伞、加衣）。

### 6.5 其他会在现场翻车的因素

| 因素 | 处理 |
|---|---|
| 营业时间 | 硬过滤：活动结束时间必须早于打烊（留 15 分钟余量）；营业时间缺失 → 不过滤，但写进风险"营业时间未知，建议出发前打电话确认" |
| 末班车 | 没有可靠的末班车数据，所以私聊里顺带问"回去怎么走"。坐地铁的人，"末班车时间"作为 time 维度的硬约束（本人确认后），离开前 30 分钟提醒 |
| 晚高峰 | 17:30–19:30 出发的开车 / 打车通勤 +20%（估算，写明是估算） |
| 排队 | 沿用现有规则；风险里写"可能排队约 20 分钟"，提醒"先到的人先取号" |
| 订位 | 人数 ≥ 6 或排座排出 ≥ 2 桌 → 发起人待办里加"订位"，附订位话术（现有 #13） |
| 夜归 | 结束时间晚于 22:30 → 群里提醒"结束得晚，回去的朋友结伴或打车，到家报个平安" |
| 费用 | 预估人均和总价写进决定书；按菜分账时提醒"先拍小票" |
| 特殊场合 | 发起人说了"生日""欢送"等 → 发起人待办里加"蛋糕 / 礼物"（只给发起人） |

## 7. 决策的输出：格式与内容

### 7.1 原则

1. **先结论，后理由。**第一行就是"什么时候、在哪、几个人"。
2. **每一条都可执行。**提醒都带上"做什么"，而不是只说"注意天气"。
3. **不确定就说不确定。**"预报小雨（只有白天 / 夜间粒度）""营业时间未知"。
4. **公开的只有聚合结论，私人的只给本人。**同一个决定，按读者生成不同版本。

### 7.2 一个决定 = 一份"决定书"（结构化，所有渠道都从它生成）

```ts
type Decision = {
  version: number;                       // 每次变更 +1
  status: "proposed" | "voting" | "final" | "revised";
  verdict: {                             // 结论
    when: Slot; where: Poi; activity: string;
    attendance: { full: number; partial: number; absent: number };   // 全程 / 晚到或早走 / 来不了（人数）
  };
  why: string[];                         // 三级准则各一句："照顾到 8/8 人""最吃亏的朋友也只是晚到 20 分钟"
  care: { cared: number; total: number; summaries: string[] };       // 聚合约束说明（现有 constraintSummaries）
  tradeoffs: string[];                   // 取舍（公开安全）
  alternatives: ProposalRef[];           // 备选方案（投票用）
  risks: Risk[];                         // 见下
  fallback?: Fallback;                   // 备案：触发条件 + B 方案 + 谁来决定切换
  coordination?: string;                 // 协商摘要（聚合）："局长私下协调了 1 位朋友"
  actions: { group: Action[]; organizer: Action[] };                 // 公开行动清单 / 发起人待办
  reminders: ReminderPlan[];             // 见第 8 节
  audit: PlanAudit;                      // 可复核
};

type Risk = {
  kind: "weather" | "closing" | "queue" | "traffic" | "booking" | "lateNight" | "unknown";
  level: "low" | "mid" | "high";
  text: string;                          // "周六白天预报小雨"
  mitigation: string;                    // "已准备室内备案：xx 桌游馆；出发前 3 小时局长再确认"
  confidence: "known" | "estimated" | "unknown";
};

type MyDecision = {                      // 只给本人
  status: "full" | "late" | "early" | "absent";
  arriveAt: string; leaveAt?: string; departAt: string; route: string[];
  needs: { text: string; result: "met" | "partial" | "unmet"; detail: string }[];  // 你的每条需求怎么被照顾的
  myActions: Action[];                   // "14:45 出发""带伞""转 ¥68 给社长"
  myReminders: ReminderPlan[];
  asks?: NegotiationAsk[];               // 局长私下问你的事（是 / 否）
};
```

### 7.3 输出到哪些地方

| 渠道 | 读者 | 内容 | 现在 |
|---|---|---|---|
| **群公告文本**（一键复制到微信） | 全群 | 结论 + 一句理由 + 风险和提醒 + 群行动 | 有，但内容单薄 |
| 局页"决定卡" | 局里的人 | 完整的公开版决定书，可展开取舍、备选、审计 | 部分有 |
| 本人"我的安排" | 本人 | MyDecision：时间路线、逐条需求结果、我的待办、局长私下问我的事 | 部分有（行程卡） |
| 发起人"待办 + 风险" | 发起人 | 冲突诊断、修复建议、订位、备案切换、风险 | 部分有 |
| 大屏 | 现场 | 结论、照顾情况、风险、审计 | 有 |
| 日历文件 | 本人 | 时间地点 + 出发提醒；变更时更新 | 有 |
| 站内信 / 私聊 | 本人 | 第 8 节的各种提醒 | 部分有 |

## 8. 提醒：什么时候、提醒谁、说什么

### 8.1 时间轴

| 时间点 | 给谁 | 内容 | 现在 |
|---|---|---|---|
| 定局时 | 全群 / 本人 | 群公告；每人的安排 | 有 |
| 定局时 | 发起人 | 待办：订位、蛋糕、确认营业时间 | 部分有 |
| 前 1 天 | 全群 | 天气复查结果（有变化才发）；还没确认的人私下提醒 | 无 |
| 前 3 小时 | 本人 | 天气 + 带什么 + 出发时间（现有出发提醒扩充） | 部分有 |
| 出发时刻 | 本人 | "该出发了" + 路线 | 有 |
| 进行中 | 本人 / 全群 | 有人晚到（聚合）；离开时间前 15 分钟提醒本人；末班车前 30 分钟提醒 | 部分有 |
| 结束时 | 全群 | 夜归提醒（晚于 22:30）；拍小票 | 无 |
| 结束后 | 本人 | 该转多少；和谁聊得来；回顾 | 有 |

### 8.2 规则

- **每条提醒都有一个行动**：带伞、出发、转账、选聊得来。
- **同一件事只提醒一次**（沿用现有的 `pushNoticeOnce` 去重），有变化才再发。
- **公开的提醒只说所有人都适用的事**（天气、打烊）；**私人的只发本人**（你的出发时间、你得几点走、你的末班车）。
- **安静时段不打扰**：23:00–8:00 的非紧急提醒顺延到早上。

## 9. 隐私约束（对决策逻辑的硬性要求）

1. **花费永远不设硬约束**：沿用 v3 规则。超预算只扣私密满意度，永远不会让人在公开视图里"来不了"，否则看谁来不了就能反推谁预算紧。
2. 公开的"照顾到 N/M 人"是聚合数，和"有人预算偏紧"同级。
3. 协商询问只用"有位朋友"的说法；询问对象、是否答应都不出公开视图。
4. 天气、营业时间等公开事实可以出现在公开输出里；它们和个人需求的叠加效果（比如"下雨 + 腿伤"）只进本人视图。
5. 所有新增的公开输出（决定书、风险、群公告）纳入反事实检验：交换检验、字面检验，以及新增的"协商不可推断"检验（谁答应了让步，换一个人答应，公开输出逐字节相同）。

## 11. 怎么证明"做精了"

1. **决策基准集**：30 个手写场景，每个写明期望结果，覆盖第 5.1 节的全部触发类型，以及外部因素（打烊、下雨的户外局、4 天外的户外局必须带备案）。每次改动都跑一遍，指标：照顾到的比例、最吃亏者的满意度、需要的让步次数、有没有排到打烊之后。
2. **理解测试集**：60 句真实说法（含糊的、拐弯的、开玩笑的、前后矛盾的），检验抽出来的 Need 对不对，尤其是硬 / 软判断和强度。
3. **输出检查**：对基准集的每个场景生成群公告和每个人的"我的安排"，人工过一遍"一眼能看懂吗、每条都能执行吗"。
4. **隐私检验**：现有 7 项 + "协商不可推断"。

---

## 12. 实施顺序

1. **Need 模型 + 理解**：私聊抽取成 Need、硬约束回问确认、理解测试集
2. **满意度 + 三级准则**：按 Need 扣分、三级准则选方案、决策基准集
3. **外部因素**：营业时间硬过滤、室内 / 户外、天气接入与四种作用方式
4. **决定书 + 输出**：`Decision` / `MyDecision` 结构、群公告、我的安排、发起人待办
5. **极端情况**：冲突诊断 + 修复菜单（先 R1 R2 R3 R6，再 R4 R5）+ 协商闭环 + "协商不可推断"检验
6. **提醒**：前 1 天 / 前 3 小时天气复查、备案切换、末班车、夜归、安静时段
7. **路演**：Demo 围绕第 5.5 节的例子 + 一次天气备案重写

## 13. 待拍板的问题

1. **保底线定多少**：50 分是拍脑袋的数，需要用基准集调。
2. **局长能自己去问多少**：建议每人每局最多 2 次、全局最多 5 次，超过就交给发起人。
3. **下雨时能不能自动切备案**：建议定局时让大家勾选"下雨自动换室内"，勾了就自动切，没勾就只通知发起人。
4. **要不要接更精细的天气源**：高德没有降水概率和逐小时预报。和风天气等可以提供，但要新申请 key。建议先用高德，够用。
5. **品类要不要交给局长定**（"随便聚聚"时局长挑吃什么 / 玩什么）：建议放第二期。
